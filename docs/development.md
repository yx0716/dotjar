# 开发与安装验收

日常使用走已安装的 dotjar；修改代码走 `npm run dev`。源码仓库可以有多个工作树，不需要卸载日常版来测试。

## 开发入口

在源码目录执行：

```sh
npm run dev
```

程序在前台运行，自动分配端口、打开浏览器，Ctrl+C 停止。页面左下角标明「开发版」、分支名和数据来源。

- 默认展示演示数据，不读取真实对话，不调用模型。
- 每个源码工作树按真实路径生成一个固定 ID，数据放在 `~/.dotjar-dev/<ID>/`。移动工作树后会使用新的开发目录，旧目录不会被自动删除。
- 日常版的 `~/.dotjar/`、旧 `~/.strata/`、安装目录和登录启动项不作为开发环境使用。
- `--no-open` 不打开浏览器，适合自动测试。

需要读取本机真实对话时：

```sh
npm run dev -- --real-data
```

这时仍不能打捞。确实要验证模型调用、接受对应额度消耗时：

```sh
npm run dev -- --real-data --allow-model
```

新生成的笔记仍写入开发目录。开发版不能把笔记输出目录改到外面，已有配置或符号链接指向外部时会报错。不要直接复制日常配置来代替这两个开关。

修改代码后，在终端停止并重新执行 `npm run dev`。开发环境禁止安装/取消系统登录自启、迁移到托管版和页面重启；它不会把前台调试进程偷偷转成后台进程。

裸源码入口（如没有隔离配置的 `npm start`）会提示改用 `npm run dev`。内部测试或高级 CLI 调试需要显式指定独立数据目录和环境，普通客户的安装命令不受影响。

## 实例之间如何隔离

每个数据目录有 `instance.json`，保存实例 ID 和环境类型。进程记录保存实例、程序来源和真实服务 PID；控制服务之前，会带本实例授权核对 HTTP 返回的实例、来源和 PID。不匹配就停止操作，不凭 PID 文件或代码修改时间接管服务。

开发与验收实例使用独立 cookie 名称，可以和日常版在同一浏览器中打开。日常版暂时保留原 cookie 名称，以兼容已安装的旧启动器、更新器和桌宠；不把两个自定义 production 目录当作两个可共用浏览器授权的环境，应使用 dev/verify 入口。

PID、日志、配置、反馈台账、消耗记录和更新锁随数据目录隔离。日常版默认登录项继续使用 `com.dotjar.web`；自定义数据目录使用带实例 ID 的名称，操作前还检查启动项是否属于当前程序。dev/verify 环境不操作系统登录项。

旧版服务没有新的身份信息时，新源码会拒绝接管。应从原安装入口停止旧服务或正常更新，不要删除 PID 文件来绕过检查。已安装托管版的签名更新协议保持兼容；本次不会自动替换其稳定启动器。

这些约束用于防止误操作，不是操作系统沙箱，无法限制同一用户主动执行的任意程序。不要在开发实例中运行不可信代码。

## 安装验收

新增的安装器支持：

```sh
dotjar install-managed --version 0.4.2 --entry-dir /指定的命令目录
```

`--version` 固定实际下载的签名发布包，而不只是 npx 安装器的源码版本。省略时仍下载最新稳定版；`--entry-dir` 省略时仍使用 `~/.local/bin`，不会覆盖已有命令。

在 macOS 源码目录执行：

```sh
npm run verify:install -- --version 0.4.2 --candidate
```

`--candidate` 将当前源码用 `npm pack` 打包，再通过 npx 调用它的安装入口，安装并校验指定的真实 GitHub 签名发布包。这验证的是「本次安装器 + 已发布程序」，不能当作当前源码已发布的证明。

新安装器正式发布后，省略 `--candidate`，才会从 `github:yx0716/dotjar#v<版本>` 获取公开安装器并测试客户流程。旧安装器没有隔离命令入口选项；脚本会在安装前拒绝运行它，避免它写入日常的 `~/.local/bin/dotjar`。

验证两个已发布版本之间的更新：

```sh
npm run verify:install -- --version 0.4.2 --from 0.4.1 --candidate
```

脚本不改 HOME，不注册登录启动项。每次创建独立的数据、程序、命令目录和 npm 缓存，依次验证：

1. npx 安装成功退出，健康检查确认版本、安装位置和数据位置。
2. 再次打开复用现有服务。
3. 停止后端口关闭，重新启动正常。
4. 指定 `--from` 时，通过已安装服务的更新 API 完成指定签名版本的升级。
5. 测试笔记和配置保留；日常版的命令入口、版本指针、PID、配置和登录项不变。

成功后停止验收服务并清理本次目录；失败时保留命令日志和 `report.json`，不盲目删除可能仍在使用的文件。加 `--keep` 可以保留成功现场。若日常版在测试期间更新或修改了被检查的配置，验收会提示关键文件变化，需要检查后重跑。

一次脚本只测试真实发布包正常安装和可选升级。崩溃回退、签名错误和进程隔离由 `npm test` 中的真实进程测试覆盖，不通过篡改线上发布包来模拟。登录/重启、Apple 公证、下载隔离属性及 Intel 实机仍要在独立 macOS 测试账号或虚拟机验证。
